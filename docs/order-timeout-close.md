# 未支付秒杀订单的定时关单

使用 Spring Task 扫描指定起点后创建、超过设定时长且仍为未支付（状态 1）的订单。按订单逐笔事务，以 `id + status=1 + 创建时间范围` 条件更新为已取消（状态 4），同事务恢复 MySQL 秒杀券库存并新增 Redis 回补任务；更新影响行数为 0 时跳过。每次扫描有数量上限，扫描游标跨周期推进并在末尾环绕；单个失败订单不会阻塞后续订单。

回补任务由同一任务轮询，每次限定批量。秒杀预扣 Lua 新增订单级预扣标记，绑定订单、券和用户。回补 Lua 检查 Redis 库存存在、无过期且为有效非负整数，购买用户在原有记录集合中，且订单预扣标记与券和用户匹配；然后用一个 MSET 同时递增库存和写入永久订单回补标记。重试发现标记时不会再次递增。回补执行成功后将数据库任务标为完成；失败时保留任务并延迟 5 分钟后重试。Redis 超时后可能已执行成功，必须保留任务并使用相同订单号重试，不能人工直接增加库存。

保留原购买用户标记。当前数据库一人一单检查也包含已取消订单，因此同一用户取消后不能重新购买同一券；恢复的库存可以由其他用户购买。RocketMQ 仍沿用原链路。本功能没有实现支付接口或支付渠道；状态条件更新仅为未来以条件更新方式实现的支付操作提供竞争保护。

## 部署与启用

默认关闭，不会扫描或修改历史订单。启用前须先检查备份并手动执行 `src/main/resources/db/order-close-migration.sql`，确认 Redis 中当前秒杀数据可信且持久化策略满足需求。迁移不自动执行。之后可通过启动参数显式设置，例如：

```text
--hmdp.order-close.enabled=true
--hmdp.order-close.start-time=2026-11-06T12:00:00
--hmdp.order-close.timeout-minutes=15
--hmdp.order-close.interval-ms=60000
--hmdp.order-close.batch-size=100
```

起点是订单创建时间的下界，必须提供，使用应用本地时区。应设置为本功能正式启用的时间，避免处理未经确认的历史订单。超时时间、间隔和批量应结合需求调整；批量限制 1 至 1000。订单表较大时，评估在 `tb_voucher_order(status, create_time, id)` 建立索引。标记仅由新版本预扣时创建，历史订单、更新前已预扣但更新后才落单的消息、新旧版本混跑时由旧节点处理的订单都可能没有该标记，即使被关单也不能自动回补 Redis，需人工对账。预扣和回补标记都需保留，不能按 TTL 自动清理；其数量会随订单增加而增长，需要监控内存并在设计安全清理方案后处理。

## 限制

这是单实例 Redis 方案：现有秒杀库存键没有 Cluster 哈希标签，回补脚本涉及多个键，不能直接用于 Redis Cluster。Redis 数据丢失、清库、数据恢复或人工改库存可能破坏回补标记和库存之间的一致性；Redis 持久化本身也有可能丢失最近写入。因此不声称跨系统强一致或永久精确一次。没有 Redis 库存或用户标记时，回补保留待处理并告警，不会凭空创建库存。回补失败应检查 `tb_order_stock_recovery` 并核对订单、数据库和 Redis 状态。

原有 Redis 预扣与 RocketMQ 发送非原子、消费者某些分支直接返回等问题不由本次关单处理解决；消息预扣后未创建的订单也无法由该任务发现。没有接入真实支付渠道时，不应将其描述为已验证的支付回调与关单并发处理。

## 验证

使用 Java 8 执行 `mvn '-Dtest=OrderCloseTest' test`，6 项测试覆盖 CAS 分支、更新库存失败抛错、扫描游标推进、配置校验、默认不加载与启用但缺少起点无法启动。测试中的数据库为模拟对象，不能证明实际事务回滚。

本次另外在临时隔离 MySQL 和 Redis 容器中，通过真实 Spring 事务代理与生产 Lua 做联调，覆盖预扣、关单、并发 CAS、数据库回滚、Redis 回补重试、丢应答后幂等、缺失和不匹配订单标记拒绝回补；隔离容器已清理。该联调脚本属于临时本机环境，并非仓库内可复现的自动化测试；未验证完整 HTTP、RocketMQ 或真实支付链路。
